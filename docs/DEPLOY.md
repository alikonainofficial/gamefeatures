# Deploying the GameFeatures demo (free tier)

This is the runbook for the public demo. Everything here runs on free plans:

| Piece | Where | Free-tier notes |
|---|---|---|
| Web app (Next.js) | **Vercel** Hobby | Personal, non-commercial use; a portfolio demo fits. |
| API (NestJS, Docker) | **Render** free web service | Spins down after 15 minutes without traffic and takes about a minute to wake. 750 free instance hours per workspace per month. |
| Redis | **Render** free Key Value | In-memory only: data is lost on every restart. That's fine here: Redis holds only the rebuildable ranking index and short-lived BullMQ jobs. |
| Postgres | **Neon** Free | 1 GB per project, scales to zero after 5 minutes idle (wakes in a few seconds). |

```
Browser ──HTTPS──> Vercel (Next.js)
   │                 └─ rewrite /api/v1/*  ──HTTPS──> Render (API, Docker) ── Neon Postgres
   └──────── Socket.IO (wss) directly ────────────────┘                  └── Render Key Value
```

REST goes through Vercel's rewrite, so the browser sees one origin and the `SameSite=Lax`, host-only refresh cookie works. Sockets connect to Render directly: they authenticate with the access token, not a cookie.

The infrastructure is in [`render.yaml`](../render.yaml) (API + Key Value) and [`apps/api/Dockerfile`](../apps/api/Dockerfile). The container runs `prisma migrate deploy` on every start, then the API. (Render's `preDeployCommand` isn't available on free services; migrating on start is safe because the free tier runs a single instance.)

---

## Pre-deploy checklist

Go through this before the first deploy and before any deploy that changes the schema or env vars.

- [ ] **CI is green** on the commit you're deploying (`gh run list --branch <branch> --limit 1`). Render's `autoDeployTrigger: checksPass` won't deploy a commit whose checks failed anyway.
- [ ] **Migrations tested on a fresh database.** CI does this twice: the e2e job migrates an empty test DB, and the `docker` job boots the image against an empty DB. For a new migration, also read its SQL: anything that drops or renames a column must follow *expand, then contract* (see Rollback).
- [ ] **Env vars set on both platforms** (tables below). In particular `API_ORIGIN` on Vercel *before* the build, and `WEB_URL` on Render.
- [ ] **Seed variables ready** if you're (re)seeding: `SEED_DEMO_PASSWORD` must match Vercel's `NEXT_PUBLIC_DEMO_PASSWORD`.
- [ ] Nothing secret is committed (`git status`; `.env` files are git-ignored).

## First deploy (plan step 6.7)

You do the account and secret steps; Claude Code can prepare and check everything else.

### 1. Neon (Postgres)

1. Create a project. **Region:** AWS Europe Central 1 (Frankfurt), to sit next to the Render region in `render.yaml` (`frankfurt`). If you prefer another region, change `region:` for *both* services in `render.yaml` before step 2 (it can't be changed after creation) and pick the Neon region nearest to it.
2. **Connect** → copy both connection strings, and add `connect_timeout=15` to each (Neon computes scale to zero and need a few seconds to wake; Prisma's default is 5 s):
   - **Pooled** (hostname contains `-pooler`) → `DATABASE_URL`, e.g. `postgresql://…@ep-xxx-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require&connect_timeout=15`
   - **Direct** (no `-pooler`) → `DIRECT_URL`, e.g. `postgresql://…@ep-xxx.eu-central-1.aws.neon.tech/neondb?sslmode=require&connect_timeout=15`
   - Don't add `pgbouncer=true`: Neon's pooler supports prepared statements, and Prisma recommends leaving it off for PgBouncer 1.21+.

### 2. Render (API + Key Value)

1. Render Dashboard → **New → Blueprint** → connect this GitHub repo and pick the branch to deploy (`improvement-plan`, or `main` once merged). Render reads `render.yaml`.
2. It asks for the `sync: false` values:
   - `DATABASE_URL`, `DIRECT_URL`: from step 1.
   - `WEB_URL`, `API_URL`: you don't know the Vercel URL yet. Enter a placeholder such as `https://example.invalid` and fix both in step 5.
   - `JWT_SECRET` / `JWT_REFRESH_SECRET` are generated by Render; `REDIS_URL` comes from the Key Value instance.
3. **Apply.** The first deploy builds the image (a few minutes), runs the migrations against Neon, and starts the API. Note the service URL, e.g. `https://gamefeatures-api.onrender.com`.
4. Check: `curl https://<render-app>.onrender.com/api/v1/health` → `{"status":"ok","db":"up","redis":"up",…}`.

If the health check shows `"redis":"down"` because the free web service can't reach the Key Value internal URL, switch to an [Upstash](https://upstash.com) free Redis: create a database, set `REDIS_URL` on the Render service to its `rediss://…` URL, and remove the `fromService` entry from `render.yaml`. BullMQ polls Redis in the background and uses part of Upstash's free command quota, so keep an eye on its usage page.

### 3. Seed the demo data (once, from your machine)

From the repo root, against the **direct** URL:

```bash
DATABASE_URL='<direct url>' DIRECT_URL='<direct url>' SEED_DEMO_PASSWORD='try-the-demo' pnpm db:seed
```

Add `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` (16+ characters; the seed refuses shorter ones with `NODE_ENV=production`) only if you want an admin account. The seed is idempotent, so re-running it is safe. It doesn't touch Redis: the ranking index rebuilds itself on the first request.

### 4. Vercel (web app)

1. **Add New → Project** → import this repo.
2. **Root Directory:** `apps/web`. Framework preset: Next.js. Leave the Build, Install and Output settings on their defaults: Vercel detects pnpm from `pnpm-lock.yaml` and installs the whole workspace, and [`apps/web/vercel.json`](../apps/web/vercel.json) sets the build command (`turbo run build --filter=@game-review/web`, which compiles `@game-review/shared` before `next build`).
3. **Environment variables** (Production; all are read at **build** time):

   | Name | Value |
   |---|---|
   | `API_ORIGIN` | `https://<render-app>.onrender.com` (no trailing slash, no `/api/v1`) |
   | `NEXT_PUBLIC_SOCKET_URL` | `https://<render-app>.onrender.com` |
   | `NEXT_PUBLIC_DEMO_MODE` | `true` |
   | `NEXT_PUBLIC_DEMO_PASSWORD` | the `SEED_DEMO_PASSWORD` from step 3 |

   Leave `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_OAUTH_PROVIDERS` unset.
4. **Deploy** and note the URL, e.g. `https://gamefeatures.vercel.app`.

`API_ORIGIN` is compiled into the routing table when Next.js builds, so changing it later needs a **redeploy**, not just a saved variable. It reaches `next build` only because `turbo.json` declares it in the build task's `env` (Turborepo 2 passes undeclared variables nowhere); CI checks the built rewrite with `scripts/check-web-rewrite.mjs`.

### 5. Point Render at Vercel

On the Render service → **Environment**: set `WEB_URL` and `API_URL` to the Vercel URL (e.g. `https://gamefeatures.vercel.app`; `WEB_URL` may be a comma-separated list if you add a custom domain later; OAuth uses the first entry). Save, which redeploys.

### 6. Verify

1. `pnpm smoke https://<vercel-app>.vercel.app`: health, game list, demo login, `/auth/me`, vote and unvote, cookie refresh, logout. Login, register and refresh allow 10 requests per minute per IP, so wait a minute before re-running it back to back.
2. **Check `TRUST_PROXY_HOPS`** (rate limits are per client IP, so a wrong value either makes all visitors share one limit or lets clients choose their own IP):
   1. On Render, add `LOG_CLIENT_IP=true` and save (it restarts).
   2. Open the Vercel site once. In Render's **Logs**, find a `[ClientIp] ip=… x-forwarded-for="…"` line for that request.
   3. `ip=` must be **your own public IP** (compare with `curl https://api.ipify.org`). Expected header: `x-forwarded-for="<your ip>, <a Vercel ip>"`.
      - `ip=` is a Vercel or Render address: the value is too low. Count the entries in `x-forwarded-for` after your IP, add 1, and set `TRUST_PROXY_HOPS` to that.
      - `ip=` is an entry to the left of your IP (only possible if something prepended one): the value is too high.
   4. **Remove `LOG_CLIENT_IP`** afterwards (IP addresses are personal data), and update `render.yaml` if the value changed.
3. By hand, two browsers: sign in as `demo_dev` in one and `demo_gamer` in the other. Open the same request in both and vote: the other browser's count changes without a reload. Change the status of a `demo_gamer` request as `demo_dev` (through `/docs` or the API; there's no status UI): `demo_gamer`'s bell badge updates live.
4. Open the site after the API has been idle for 15+ minutes: the "Waking up the free demo server" banner appears, then the page reloads once the API answers.

### 7. Record the URLs

Put the Vercel URL in the README's **Live demo** section (plan step 7.1).

## Environment variables

**Render (API).** Set by `render.yaml` unless marked *dashboard*.

| Name | Value | Notes |
|---|---|---|
| `NODE_ENV` | `production` | Secure cookies, quieter Prisma logging, seed guardrails. |
| `DATABASE_URL` | *dashboard* | Neon **pooled** URL. |
| `DIRECT_URL` | *dashboard* | Neon **direct** URL (migrations on start). |
| `REDIS_URL` | from the Key Value | Or an Upstash `rediss://` URL. |
| `JWT_SECRET`, `JWT_REFRESH_SECRET` | generated | Rotating them signs everyone out. |
| `WEB_URL` | *dashboard* | Vercel URL(s), comma-separated. CORS, socket CORS, OAuth redirect (first entry). |
| `API_URL` | *dashboard* | The Vercel URL too (the OAuth callback must come back through the rewrite). |
| `TRUST_PROXY_HOPS` | `2` | Verified in step 6. |
| `THROTTLE_TTL_MS`, `THROTTLE_LIMIT` | `60000`, `100` | General per-IP limit. |
| `AUTH_THROTTLE_LIMIT` | `10` | Login/register/refresh per minute per IP. |
| `PORT` | set by Render | The API listens on it. |
| `LOG_CLIENT_IP` | unset | `true` only while checking `TRUST_PROXY_HOPS`. |
| `RAWG_API_KEY`, `RAWG_TIMEOUT_MS` | optional | Game search/import from RAWG; the seeded games don't need it. |

OAuth (`GOOGLE_*`, `TWITCH_*`) and push (`FIREBASE_*`) stay unset in the demo.

**Vercel (web).** See step 4: `API_ORIGIN`, `NEXT_PUBLIC_SOCKET_URL`, `NEXT_PUBLIC_DEMO_MODE`, `NEXT_PUBLIC_DEMO_PASSWORD`.

## Later deploys

- Push to the deployed branch. Vercel builds every push; Render deploys once the commit's CI checks pass (`autoDeployTrigger: checksPass`). The container applies any new migrations on start.
- After a deploy: `pnpm smoke <vercel url>`.

## Switching the deployed branch

The first deploy tracked `improvement-plan`. To deploy from `main` instead (for example after merging the pull request):

1. **Merge first**, so `main` already contains the deployable code. (Switching first would make Render build the old `main`, which has no Dockerfile.) Keep the old branch until step 3 is done.
2. **Vercel:** project → **Settings → Environments → Production → Branch Tracking** → `main` → **Save**. Pushes to `main` now create production deployments; to deploy right away, **Deployments → Create Deployment** with branch `main`.
3. **Render (service):** `gamefeatures-api` → **Settings → Build → Source → Edit** → branch `main` → save. Render then deploys `main` once its CI checks pass.
4. **Render (Blueprint):** the Blueprint (`render.yaml` sync) is linked to the branch it was created from. If its **Settings** page lets you change the branch, set it to `main`. If not, it stays linked to the old branch: the service still deploys code from `main`, but later `render.yaml` edits won't sync on their own, so apply them in the service's settings (or create a new Blueprint from `main`). In that case don't delete the old branch, since the Blueprint still points at it.
5. Run `pnpm smoke https://<vercel-app>.vercel.app`.

## Rollback

**Triggers.** Roll back when any of these happen after a deploy:

- `/api/v1/health` returns 503 for more than 5 minutes after the server has woken up.
- The smoke test fails on login or voting.
- 5xx responses on the main flows (game list, request page, voting, sign-in) in Render's logs or the browser.

**How.**

- **API (Render):** service → **Events** (or Deploys) → pick the last good deploy → **Rollback**. Consider turning auto-deploy off until the fix lands, or the next push redeploys.
- **Web (Vercel):** project → **Deployments** → last good deployment → **Instant Rollback**.
- **Database:** migrations are **forward-only**; there is no automatic down-migration. Ship schema changes *expand, then contract*: first add the new column or table and deploy code that works with both shapes; drop the old one in a later release once nothing uses it. Then rolling the code back never meets a schema it can't read. For a real mistake, Neon can restore the branch to a point in time (Free plan: a short history window; see Neon's docs) or you can write a corrective migration.
- **Redis:** nothing to roll back. It's a derived index; flushing it (or a restart) is always safe.

## Known caveats

- **Cold starts:** the first request after 15 idle minutes waits about a minute (Render), plus a few seconds if Neon has also scaled to zero. The web app's banner covers it.
- **Direct API calls can dodge per-IP limits.** `TRUST_PROXY_HOPS=2` trusts the last two `X-Forwarded-For` entries. Requests through Vercel are fine, but someone calling the `onrender.com` URL directly controls the first of those entries and can rotate it. A shared-secret header added by Vercel and checked by the API would close this; it's out of scope for the demo.
- **Single instance:** sockets and BullMQ assume one API instance (no Socket.IO Redis adapter).
- **Key Value is in-memory:** a restart loses queued notification jobs that hadn't run yet (rare; they run within seconds).
- **Free hours:** 750 instance hours per workspace per month is enough for one always-on service, but not for several.
